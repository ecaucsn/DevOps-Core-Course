> **Цель:** Построить бессерверный HTTP API на глобальной периферии Cloudflare — в V8 isolate, а не в контейнере — и подкрепить его вашими измерениями Kubernetes из лабораторной 9 в честном сравнении.
> **Результат сдачи:** PR из `lab17` с `edge-api/` (проект Worker) и `docs/LAB17.md` (сравнение + доказательства).

## Обзор

Cloudflare Workers выполняет ваш код в **V8 isolate** — изолированной песочнице JS-кучи внутри уже запущенного процесса `workerd` в 330+ точках присутствия. Холодный старт — **<5 мс**, нижняя граница памяти — ~3 МБ на isolate, и регион выбирать не нужно: каждый деплой глобальный. Это противоположный конец спектра абстракций по сравнению с Kubernetes, который вы строили в лабораторных 9–16.

В этой лабораторной вы отработаете:
- Создание заготовки Worker с помощью **Wrangler 4.95+** (4.x по умолчанию **local-first**; `--remote` включается явно)
- Написание обработчика в форме `export default { async fetch(...) }` из среды выполнения V8
- Подключение состояния на периферии с помощью **Workers KV** + секретов Wrangler
- Чтение метаданных запроса на периферии (`request.cf.colo`), чтобы доказать модель маршрутизации по PoP
- Получение **честного, измеренного сравнения** Workers и вашего развёртывания K8s из лабораторной 9

> ⚠️ **Область:** эта лабораторная **не** поставляет ваш Docker-образ из лабораторной 2. В Workers нет `FROM`, нет ingress, нет HPA, нет файловой системы. Вы построите нативный для Workers API, который сохраняет те же эксплуатационные аспекты (маршруты, health check, конфигурация, состояние, логи, развёртывания) в модели периферии — и опишете, где это перестраивает задачу.

> ⚠️ **Это бонусная / экзаменационная альтернативная лабораторная.** Выполните обе — лабораторную 17 (12 баллов) и лабораторную 18 (12 баллов) — на требуемом уровне, чтобы заменить финальный экзамен.

## Задача 1 — Создать заготовку, собрать и развернуть Worker API (4 балла)

### 1.1 — Создание заготовки проекта

Используйте C3 (`create-cloudflare`) с шаблоном **Hello World / Worker only**:

```bash
npm create cloudflare@latest -- edge-api
cd edge-api
```

При появлении запроса выберите: *Hello World example* → *Worker only* → **JavaScript** (можете использовать TypeScript, если предпочитаете; скелет ниже — JS) → Git: **Yes** → Deploy now: **No**.

Затем:

```bash
npx wrangler --version   # убедитесь, что 4.95 или новее
```

> Почему 4.95+? Wrangler 4.x переключил `wrangler dev` на **local-first** — он запускает ваш Worker в `workerd` на вашей машине. Флаг `--remote` теперь включается явно. Если вы на устаревшей 3.x, `dev` бьётся в preview-инфраструктуру Cloudflare, которая ведёт себя иначе (и расходует запросы).

### 1.2 — Настройка `wrangler.toml`

Скаффолдер C3 генерирует `wrangler.jsonc`. Можете оставить его или переименовать в `wrangler.toml` — работает и то и другое; эта лабораторная использует TOML для краткости. Откройте файл и заполните значения сами:

```toml
# wrangler.toml — ВАША ЗАДАЧА: заполните каждое значение
name = "___"                    # ВАША ЗАДАЧА: выберите имя worker (строчные буквы, дефисы, в духе вашего ника)
main = "___"                    # ВАША ЗАДАЧА: путь к вашему входному файлу (например, src/index.js)
compatibility_date = "___"      # ВАША ЗАДАЧА: дата ISO — фиксирует поведение среды выполнения; выберите сегодняшнюю (YYYY-MM-DD)

# Простые текстовые переменные (задача 2 добавит настоящие)
[vars]
APP_NAME = "edge-api"
```

> **Почему `compatibility_date`?** Она фиксирует семантику среды выполнения `workerd`, чтобы Cloudflare могла выпускать новые значения по умолчанию, не ломая ваш Worker. Выбрать сегодняшнюю дату — нормально; никогда не оставляйте её пустой.

### 1.3 — Написание обработчика `fetch`

Откройте `src/index.js`. Заготовка C3 даёт вам «Hello World» — **удалите его**. Точка входа Worker — единственный объект, экспортируемый как `default`, с одним асинхронным методом `fetch(request, env, ctx)`. Вот вся форма:

```javascript
// src/index.js
export default {
  async fetch(request, env, ctx) {
    const url = new URL(request.url);

    // ВАША ЗАДАЧА: маршрутизируйте по url.pathname для "/", "/health", "/echo"
    // ВАША ЗАДАЧА: GET /         → Response.json с информацией о сервисе
    //            ключи (повторяют форму лабораторной 1): { service, version, framework, runtime, edge: { colo }, path }
    // ВАША ЗАДАЧА: GET /health   → Response.json({ status: ___, edge: true }) с HTTP 200
    // ВАША ЗАДАЧА: /echo
    //            POST → вернуть тело запроса обратно (тот же Content-Type)
    //            GET  → 405 Method Not Allowed, тело JSON { error: ___, allow: ___ }
    // ВАША ЗАДАЧА: всё остальное → 404 с телом JSON { error: ___, path: url.pathname }

    return ___;
  }
};
```

Требования:

- **`GET /`** возвращает как минимум пять ключей верхнего уровня: `service`, `version`, `framework` (`"cloudflare-workers"`), `runtime` (`"v8-isolate"`), `edge.colo` (читается из `request.cf?.colo` — см. примечание ниже) и `path`. Сохраните форму JSON `/` из лабораторной 1, чтобы контраст был честным.
- **`GET /health`** возвращает `{ status: "ok", edge: true }` с HTTP 200. Именно это `wrangler tail` поможет вам наблюдать в задаче 3.
- **`POST /echo`** читает тело запроса (`await request.text()` или `await request.json()`) и возвращает его. `GET /echo` возвращает **405** с семантикой `Allow: POST` в JSON.
- **Всё остальное** возвращает **404** с телом JSON (никогда не HTML — тот же урок, что в лабораторной 1).

> **`request.cf?.colo`** заполняется Cloudflare на реальной периферии. В `wrangler dev --local` он `undefined` или заглушка (`"TBS"`). Это ожидаемо; ваш обработчик `/` должен использовать опциональную цепочку, чтобы не падать.

> **`Response.json(obj, init?)`** — современный способ вернуть JSON из Worker — сам устанавливает `Content-Type: application/json`. Доступен начиная с `compatibility_date: 2022-01-31`. Если вы установите более раннюю дату, вам придётся вручную писать `new Response(JSON.stringify(obj), { headers: { "content-type": "application/json" } })` — ещё одна причина зафиксировать недавнюю дату в 1.2.

### 1.4 — Локальный запуск на `workerd`

```bash
npx wrangler dev
```

Wrangler поднимает процесс `workerd` на `http://localhost:8787`. Это **та же** среда выполнения V8 isolate, которую Cloudflare запускает на периферии — локальная разработка достоверно повторяет поведение продакшена (за вычетом `request.cf` и глобальной маршрутизации).

`ВАША ЗАДАЧА`: пройдите каждый маршрут через `curl` и зафиксируйте JSON. Рекомендуемые проверки:

- `curl -s http://localhost:8787/ | jq .`
- `curl -s http://localhost:8787/health | jq .`
- `curl -s -X POST -H 'content-type: application/json' -d '{"ping":42}' http://localhost:8787/echo | jq .`
- `curl -s -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8787/echo` (GET → ожидается `HTTP 405`)
- `curl -s -o /dev/null -w "HTTP %{http_code}\n" http://localhost:8787/nope` (ожидается `HTTP 404`)

### 1.5 — Глобальное развёртывание

```bash
npx wrangler login         # OAuth в браузере; открывает localhost-callback
npx wrangler whoami        # подтверждает аккаунт + показывает ваш поддомен workers.dev
npx wrangler deploy
```

> ⚠️ **Подводный камень headless / удалённой ВМ:** `wrangler login` открывает браузер локально и слушает `127.0.0.1:8976` для OAuth-callback. Если вы подключены по SSH к удалённой ВМ без локального браузера, callback никогда не дойдёт до вашего браузера. Два варианта: (a) `ssh -L 8976:localhost:8976 <user@host>`, чтобы пробросить OAuth-callback на ваш ноутбук, или (b) экспортируйте `CLOUDFLARE_API_TOKEN=<token>` из токена, созданного в дашборде (Account → API Tokens → шаблон "Edit Cloudflare Workers"). Опишите путь, который вы выбрали, в §1.6.

Вывод печатает `https://<worker-name>.<your-subdomain>.workers.dev`. Обратитесь к нему через `curl` и подтвердите тот же JSON — за исключением того, что `edge.colo` теперь **настоящий** код PoP (`"FRA"`, `"WAW"`, `"SVO"`, ...).

## Задача 2 — Конфигурация, секреты и состояние на периферии (3 балла)

### 2.1 — Почему это важно

Ваш Worker теперь отвечает. Следующая проверка — сможете ли вы дать ему **конфигурацию** (vars), **учётные данные** (secrets) и **состояние** (KV), никогда не помещая их в Git. Это та же задача разделения ответственности, которую вы решали в лабораторных 1 (переменные окружения), 11 (секреты OpenBao) и 12 (ConfigMaps + PVC) — примитивы просто в форме периферии.

### 2.2 — Текстовая переменная

Вы уже добавили `APP_NAME` в `wrangler.toml` в 1.2. `ВАША ЗАДАЧА`: прочитайте её внутри Worker (`env.APP_NAME`) и выведите в поле `service` вашего `GET /`. Одним предложением в `docs/LAB17.md` скажите, почему vars **непригодны для секретов** (подсказка: они в дашборде + в Git + читаются любым коллаборатором).

### 2.3 — Секреты Wrangler

Создайте **два** секрета. Wrangler запросит у вас значение — оно никогда не попадёт в ваш репозиторий:

```bash
npx wrangler secret put ___        # ВАША ЗАДАЧА: назовите свой первый секрет
npx wrangler secret put ___        # ВАША ЗАДАЧА: назовите свой второй секрет
npx wrangler secret list           # только имена, без значений
```

Затем прочитайте их внутри Worker. Привязки появляются на `env`:

```javascript
// ВАША ЗАДАЧА: в вашем обработчике fetch прочитайте секрет, который вы добавили выше
const token = env.___;             // ВАША ЗАДАЧА: должно совпадать с именем в `wrangler secret put`
```

Покажите один из них в **закрытом** маршруте — например, `GET /admin` возвращает 401, если `request.headers.get("authorization") === \`Bearer ${env.YOUR_SECRET}\``. Смысл — доказать, что секрет проходит по цепочке от `wrangler secret put` → `env` → обработке запроса.

> **Локальная разработка + секреты:** `wrangler dev` читает локальные переопределения из `.dev.vars` (файл в gitignore, формой похожий на `.env`). Для настоящего развёртывания учитывается только `wrangler secret put`.

### 2.4 — Workers KV (обязательно)

KV — это eventually-consistent хранилище ключ/значение Workers — правильный примитив для флагов, счётчиков и небольших блоков конфигурации. Настройка в два шага: создать пространство имён, затем привязать его.

```bash
npx wrangler kv namespace create ___      # ВАША ЗАДАЧА: выберите имя привязки (например, SETTINGS)
```

Команда печатает фрагмент конфигурации. Скопируйте **id**, который она выдаёт, в `wrangler.toml`:

```toml
[[kv_namespaces]]
binding = "___"     # ВАША ЗАДАЧА: то же имя привязки, что вы использовали выше — именно это раскрывает env.<binding>
id      = "___"     # ВАША ЗАДАЧА: id пространства имён, который только что напечатал Wrangler (32-символьная hex-строка)
```

Затем напишите маршрут `/counter`, который инкрементирует счётчик посещений на основе KV:

```javascript
// ВАША ЗАДАЧА: внутри fetch обработайте url.pathname === "/counter"
// 1. прочитайте текущее значение через env.<binding>.get("visits") (возвращает строку или null)
// 2. вычислите следующее целое
// 3. запишите обратно через env.<binding>.put("visits", String(n))
// 4. верните Response.json({ visits: n })
```

Полный цикл из CLI, чтобы убедиться, что пространство имён реально:

```bash
npx wrangler kv key put --binding=___ "visits" "0"        # ВАША ЗАДАЧА: имя привязки
npx wrangler kv key get --binding=___ "visits"            # ВАША ЗАДАЧА: та же привязка
```

> **D1, R2, Durable Objects** — все живут на одной модели `env.<binding>`:
> - **D1** — SQLite на регион, реплицируемый. Используйте, когда нужны join'ы.
> - **R2** — S3-совместимое блоб-хранилище, **без платы за исходящий трафик**. Используйте для ресурсов/резервных копий.
> - **Durable Objects** — строго согласованные stateful-акторы. Используйте для чат-комнат, таблиц лидеров, rate-limiter'ов.
> KV — правильный выбор здесь; бонусная задача позволит вам заменить его одним из других.

### 2.5 — Доказательство работы

**Вставьте в `docs/LAB17.md`:**

- вывод `npx wrangler secret list`, показывающий **имена** ваших двух секретов (значения не должны появляться)
- `curl`, доказывающий закрытый маршрут из 2.3 — один вызов без заголовка (401), один с ним (200)
- полный цикл `npx wrangler kv key put` / `kv key get` из 2.4 (иллюстративные ID подойдут; ваши ID будут другими)
- `curl http://localhost:8787/counter` (или ваш развёрнутый URL), вызванный **три раза** — третий ответ должен показать `visits: 3` *и* должен продолжаться, а не сбрасываться, после повторного развёртывания, если вы развёртывали
- одно предложение о том, почему vars непригодны для секретов

## Задача 3 — Наблюдаемость, эксплуатация и сравнение с K8s (3 балла)

Это отдача от лекции 16. Workers и K8s решают одну задачу (запуск моего HTTP-кода в продакшене); они платят очень разные цены.

### 3.1 — Живые логи

Добавьте хотя бы один вызов `console.log()` в ваш обработчик `fetch` — логируйте путь и (возможно, undefined) colo:

```javascript
// ВАША ЗАДАЧА: добавьте console.log как минимум с путём и request.cf?.colo
console.log(___);
```

Затем в другом терминале:

```bash
npx wrangler tail
```

Обратитесь к любому маршруту из третьего шелла. Строка лога стримится с периферии почти в реальном времени.

`ВАША ЗАДАЧА`: зафиксируйте **одну** строку `wrangler tail` — вставьте буквальную запись лога (с таймстампами и всем прочим) в `docs/LAB17.md`.

### 3.2 — Версии и откат

Разверните как минимум **две** версии вашего Worker. Незначительное изменение между ними подойдёт (поднимите поле `version` в `GET /`). Затем перечислите и откатите:

```bash
npx wrangler deployments list      # ВАША ЗАДАЧА: зафиксируйте это — ID версий + таймстампы
npx wrangler rollback              # ВАША ЗАДАЧА: зафиксируйте это — подтверждает откат
```

### 3.3 — Таблица K8s против Workers (весь смысл)

<details>
<summary>⚠️ Частые подводные камни (из реальных прогонов)</summary>

- **Нет файловой системы в V8 isolate.** `import fs from "node:fs"` падает при развёртывании. Нет `/tmp`. Если вам нужно что-то сохранить, это KV/D1/R2/DO или ничего.
- **По умолчанию нет Node API.** `Buffer`, `process`, `crypto` (в варианте Node) отсутствуют. Чтобы использовать подмножество, добавьте `compatibility_flags = ["nodejs_compat"]` в `wrangler.toml` — это включается явно не просто так; V8 isolate — это не Node.
- **KV — eventually consistent.** `put`, за которым сразу следует `get` из другого PoP, может вернуть старое значение **до ~60 секунд**. Нормально для счётчиков и флагов; неправильно для «нажал ли пользователь кнопку покупки». Используйте Durable Objects, когда нужно read-your-writes.
- **`Response.json()` Content-Type.** Автоматически устанавливается начиная с `compatibility_date: 2022-01-31`. Если вы зафиксировали более раннюю дату (или скопировали древние примеры), вам придётся задать `content-type: application/json` вручную. Зафиксируйте недавнюю дату в `wrangler.toml`.
- **`wrangler dev` по умолчанию локальный в 4.x.** Он запускает `workerd` на вашем ноутбуке — `request.cf` — заглушка, KV — локальный эмулятор на SQLite, секреты берутся из `.dev.vars`. Используйте `wrangler dev --remote`, только если вам нужны настоящие метаданные периферии в разработке (считается против квоты).
- **`wrangler secret put` требует, чтобы Worker уже существовал на Cloudflare.** Если вы ни разу не запускали `wrangler deploy`, команда секрета падает. Разверните заглушку, затем добавьте секреты, затем разверните настоящую версию.
- **Поддомен `workers.dev` занимается один раз на аккаунт.** Первое развёртывание предлагает выбрать `<you>.workers.dev`. Позже его нельзя изменить без поддержки на уровне аккаунта.
- **`request.cf?.colo` равен `undefined` в локальной разработке** (или константа-заглушка `"TBS"`). Всегда используйте опциональную цепочку.

</details>
